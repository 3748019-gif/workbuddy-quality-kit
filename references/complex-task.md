# 复杂任务与跨会话续接

仅在多阶段、跨文件、可复运行工具、复杂决策或确需暂停恢复时使用。沿用已有任务记录，不另起一套日志。任务特定规则写在任务目录，不能写入全局指令或个人记忆。

## 先用可检验的规则缩小问题

列清输入、必须交付项、约束和完成条件。把同级冲突与缺失信息隔离，完成确定部分。计算任务把匹配、时间边界、舍入顺序、冲突优先级写成少量明确规则。输入校验不能擅自添加非负、非空等业务限制；区分结构非法与规则允许的无解。数据量大时先用程序统计，不依赖逐行心算；独立复算代表性边界例即可。

开始长任务时先落盘简短节点，再按可检验的小阶段推进。代码先保存能运行的最小版本，再补边界与核验；其他任务先保存有用的中间产物。避免在首次保存前一次性生成大量推理、脚本和日志，让中断后仍有可接续的实际工作。

把“可运行核心”和“完整交付”分成真实的保存点：先记录任务节点，保存并运行核心计算与最少结果，确认可回读后再扩展界面、文档和恢复功能。用实际已保存路径更新同一节点，不能把尚在生成的长代码当成可续接成果。阶段验收失败保留原始错误及受影响项；下一会话先确认当前源码可运行，再接着扩大测试，不照抄旧的通过数字。

生成工具应至少用一份未用于编写时的输入复跑；正例、无解/异常和重复运行各覆盖实际风险。核验期望值须来自规则推导、独立算法或明确手算样例，不能直接用被测程序结果生成“正确答案”。优化/排程任务区分可行与最优：检查全部硬约束，再用穷举、可核对下界或其他适用证据支持最优性；启发式只能声称所得可行解，不编造搜索数量。

读入并验证必要结构后再发布成品。坏JSON、缺列等输入结构错误不能破坏此前成功产物；业务规则允许的pending不等于工具执行失败。关键自检失败应阻止发布并保留此前成功结果。用临时文件或独立候选目录写入、回读、核对后发布，合理保护多文件一致性；不把未完成候选标为最终结果。只管理已知输出，用户新增文件不得被目录清理删除。

连续写多个最终文件时，异常处理中的回滚只覆盖进程仍能运行的错误，不覆盖突然退出或断电。确需可恢复发布时，先把完整候选及发布前有效版本保存到任务内独立代次目录，落盘版本清单，再按明确方式切换；重启后依据清单识别完整代次，不把混合版本当成成功。交付格式不能整体切换时，保留完整旧版及发布中状态，并明确恢复步骤与局限。用隔离副本中途终止生成进程检查这一点即可；不要为测试退出实际办公软件、重启系统或关闭安全机制。普通单文件短任务不强加多版本发布框架。

可复用scripts/task_guard.py的publish_set，避免每次重写只靠try/except的“事务”。将模块随工具交付。输入、输出和专用workdir使用任务相对路径；输出父目录与workdir先在允许范围内建好，输出不得位于该专用workdir中。计算前先snapshot输入（含规则），把该input_state传入发布；payloads是“相对路径→完整bytes”的映射，validate接收“相对路径→已落盘候选Path”，必须逐项检查实际内容并明确返回True。示意调用：

BASELINE = task_guard.snapshot(ROOT, ['input'])
OUTPUT_BASELINE = task_guard.review_outputs(ROOT, OUTPUT_NAMES)
完成本任务计算与序列化，得到PAYLOADS，并实现check_saved_candidates
result = task_guard.publish_set(ROOT, PAYLOADS, inputs=['input'], workdir='work/publications', input_state=BASELINE, output_state=OUTPUT_BASELINE, validate=check_saved_candidates)

基线必须早于业务文件读取和计算，并原样传入；不能在publish封装里才快照，或发布前重新快照来消除变化。这样计算期间普通输入改动也会拒绝陈旧发布，而不只是检查发布过程中的改动。

它保留完整候选、旧代次及state.json；正常写入错误会尝试恢复旧代次，突然退出后prepared状态会阻止新发布。恢复先status，输入未变且候选仍有效可commit，输入已变可rollback后按新输入重算；后来人工修改或删除输出时拒绝自动恢复，保留现场并处理冲突。journal采用函数实际返回的相对路径，不猜目录名：

PY task_guard.py recover --root ROOT --journal JOURNAL --action status
PY task_guard.py recover --root ROOT --journal JOURNAL --action commit
PY task_guard.py recover --root ROOT --journal JOURNAL --action rollback

status只读，prepared或冲突不是完成；恢复命令不用于撤销已经完成的历史版本。工具核验文件版本和输入保留，不判断业务规则或合并人工文字，validate不能用无条件True代替实际验收。代次保留用于恢复；同字节重复发布不增加代次，不为清理历史删未知文件。路径别名、未知状态文件或跨文件系统等不受支持情况会拒绝并保留。它不提供多文件瞬时原子可见性，不认证断电恢复、并发恶意改写、ACL或扩展属性；尚未恢复的目录不能当成完整最终成果消费。

验收描述须与实际方法一致：同一实现改参数重跑不等于独立算法，约束检查不等于最优性证明，内存序列化检查不等于落盘回读。未排入或未采用的原因须有证据，不能套用未经验证的解释；时间与运行统计从实际记录取得，不猜测。

可复运行工具在写入前解析输入、输出的真实路径及符号链接，拒绝输出指回输入区域；已存在的目录及父目录还要比较文件身份，兼容大小写别名。临时文件用系统安全创建的唯一名称；不可覆盖固定名称的既有临时文件，也不跟随其链接写入别处。只清理本次实际创建的文件。

候选成果第一次达到可回读、可继续的状态时，更新已有节点，列入它的路径和版本，不只跟踪预定最终文件。旧草稿因数据更新而过期，其人工补充仍可能有效：恢复时检查现有草稿和正式成果中后来加入的文字或批注，不只检查独立的说明.txt。将可明确区分的人工部分合并到新版本并实际回读确认；无法区分时保留旧文件与独立新候选，明确尚未合并，不宣称“人工修改全部保留”。不要因节点未及时更新而忽略已经存在的产物。

覆盖已有报告前，在同一节点列一份很短的人工内容去向：来源文件与段落/批注、目标文件、保存后确认结果。对Word读取实际段落和批注，对表格检查相关单元格及批注；不只搜索文件名或独立备注。没有可信旧版可供差分时，逐一查看已有候选与正式成果的可保留内容，不能据此假定没有人工修改。结果更新后既检查新业务值，也检查应继承的人工文字确实在交付中；未解决冲突须保留并说明。

读取并合并已有成果里的人工内容之前，还要调用review_outputs(ROOT, OUTPUT_NAMES)，OUTPUT_NAMES为本次实际最终成果相对路径列表，将返回的output_state原样传入publish_set。已有成果本来就是本次授权更新目标，不可把它们塞进不可变inputs来绕开输入输出分离。发布器会比较“阅读人工内容之前”的成果版本与发布前版本：计算期间新增、删除或修改了成果，就拒绝陈旧覆盖并保留后来修改。只有输入基线而没有这个成果基线，不能保护计算期间才加入的人工段落。基线不能在发布函数内部或临近发布时才拍；拒绝后先核对实际变化、合并或保留候选，再决定是否重新计算，不重拍基线消除失败。普通无人工继承的全新单文件任务不强加该步骤。

## 最小可续接节点

在阶段完成、重要规则变化和暂停时写入或更新现有task_state.md。内容应足以让一个没有旧聊天记录的新会话继续：

- 当前目标、用户限制与完成条件；规则文件及生效范围。
- 输入相对路径和SHA-256；重要产物路径、完成/草稿状态及最后确认哈希。文件多时引用一份清单，不在多处重复抄写。
- 简单依赖关系，例如数据与规则→明细和汇总→报告；不为短任务绘制复杂依赖图。
- 实际已执行的命令/解释器与结果、未决冲突和未验证范围。
- 最后完成阶段、当前阻碍、下一步，明确暂停或完成；重试可能影响哪些文件。

节点不保存账号、密钥、无关个人记忆或整个环境。脚本要用当前机器支持的运行时，不能把旧电脑绝对路径当可移植保证。

多个阶段已有落盘产物时，可按需使用task_guard.py的checkpoint/resume只读版本检查，减少手工漏记。依赖文件使用任务相对路径，例如{"output/data.json":["input"],"output/report.txt":["output/data.json"]}；每个受跟踪输出必须列依赖。先保存实际有效产物，再执行：

PY task_guard.py checkpoint --root ROOT --inputs input --outputs output/data.json output/report.txt --dependencies work/dependencies.json > ROOT/work/checkpoint.json
PY task_guard.py resume --root ROOT --state work/checkpoint.json

保存节点前同样检查重定向目标位于本任务且不覆盖输入或已有用户文件。checkpoint只记录已存版本，不是质量通过证明；简单节点无需强制转换成JSON。resume返回非零或passed=false表示需处理实际变化；changed_inputs、modified_outputs_preserve_and_review、missing_outputs与recheck_outputs分别用于定位，不能据此直接覆盖或恢复文件。依赖关系应覆盖实际来源；错误或不完整的依赖图不会自动得到正确业务结论。新增的输入、用户手改以及缺失文件仍要按下文检查。

## 从新会话恢复

先读最新指令与节点，然后核对当前输入及关键产物。文件变化、缺失或新增时，先辨明来源和影响：输入/规则变化会使相应结果和报告过期；规则只变局部也不能把其他范围一并替换。未变化且证据充分的部分可复用，但不能把旧qa.json的成功状态当作当前检查。

自己生成的文件也可能被用户手改。与最后确认的哈希不同，先读差异：保留用户新增内容，做能明确限定范围的合并；无法判断则在独立候选文件完成可做部分并集中说明冲突，不覆盖整份文件或恢复旧备份。不要自动恢复被删除的文件，先确认它仍是本轮明确需要的交付。

恢复后重算受影响的业务结果，并从最终文件复核来源、范围与合计；多个交付须来自同一输入版本。只有相关文件都核验完毕，才更新当前节点和交付状态。没有新变化不反复全量重验；记录新的证据即可。

遇到调用卡顿或兼容错误，先检查最近一次实际进展、已落盘文件及明确错误；保存现场后才调整方法。重试须有停止条件，不无休止重发同一调用，不为了通过测试移除安全环境或扩大权限。明确区分真实故障后恢复、主动暂停续接和仅目录模拟，不能把其中一种写成另一种。
